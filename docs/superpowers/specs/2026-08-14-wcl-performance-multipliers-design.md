# WCL performance multipliers — design

**Date:** 2026-08-14
**Status:** Approved design, in implementation

> **Revision 2026-08-14 (during implementation).** The original design divided each player's
> parse by the **global spec median** taken from WCL's ranking population. A live probe of the
> API killed that approach: `characterRankings.count` is the number of entries on the requested
> page, not the size of the ranking population, and the API refuses any page beyond 20 — so at
> most 2,000 entries per spec/boss are reachable. Popular specs have on the order of 200,000
> ranked parses, making the reachable slice the top ~1%; its "median" is roughly the 1,000th
> best parse in the world, not an average player. No paging scheme fixes this, because the
> data simply is not exposed. §2 now normalizes against the raid's own roster using the
> engine's calibrated `BASELINE` table for cross-spec scale. §3–§6 follow from that change.

## 1. Problem

The group optimizer v2 scores players as `BASELINE[spec] × mult(p) × buffs`, treating every
player of a spec as identical unless the raid leader hand-edits the per-player multiplier
(`state.playerMeta[name].mult`, UI range 0.5–2.0, default 1.0). In practice players differ a
lot: a well-played mage can out-deliver a BiS warlock. Buffs and premium group seats should
flow to the players who actually produce the most damage. This feature fills the existing
multiplier automatically from Warcraft Logs data, as an **editable prefill** — the engine and
score model are untouched.

## 2. The multiplier definition

```
mult(p) = mean over bosses B of  ratio(p, B)

ratio(p, B) = playerMedianAmount(p, B) / ( BASELINE[spec(p)] × c(B) )

c(B)        = median over rostered players q with a qualifying parse on B of
              ( playerMedianAmount(q, B) / BASELINE[spec(q)] )
```

- `playerMedianAmount(p, B)` = the median `amount` (DPS) of p's ranked parses on boss B
  **within the last 4 weeks**, on the spec p is rostered as. Median, not best: one lucky
  parse must not crown anyone.
- `BASELINE[spec]` is the engine's existing calibrated simulated DPS per spec
  (`assignments-engine.js`, generated by the wowsims calibration harness). It carries the
  **cross-spec** scale — it is what makes a tank's 700 DPS and a hunter's 2,000 DPS
  comparable.
- `c(B)` is a single scalar per boss, fitted from the roster itself. It absorbs everything
  that is true of the boss rather than the player: fight length, add phases, target count,
  and the raid's overall gear level on the night. Taking it as a **median** across the
  roster keeps one outlier from dragging the whole boss.
- A boss contributes only when at least **3 rostered players** have a qualifying parse on
  it. Below that, `c(B)` is fitted from too little data to mean anything — with one player
  it is degenerate, forcing that player's ratio to exactly 1.0.
- Averaged across every qualifying boss where the player has ≥1 qualifying parse.
- Clamped to [0.5, 2.0] (the existing UI range), rounded to 0.01.

**What 1.0 means, and the honest caveat.** Under this definition `1.0` is "an average member
of *this roster*, after correcting for spec with the sim baseline" — not "an average player of
this spec worldwide", which is what the original design promised and what the existing input
tooltip says. Where the wowsims baseline misjudges a spec, that error shows up in the
displayed number: if the sim overrates Beast Mastery by 20%, a perfectly average BM hunter
displays ≈0.83. The **ranking is still correct** — substituting the definition into the engine
gives `BASELINE[spec] × mult = c(B)-scaled real DPS`, so `BASELINE` cancels out and the score
tracks the player's actual logged damage — but the number a human reads is roster-relative,
and the UI must say so rather than repeat the old wording.

**Mixed rosters are not internally comparable.** Substituting the definition shows
`mult ≈ observedDPS / BASELINE[spec]` (divided by the boss scale), which was confirmed
empirically: a 15-player live run reproduced every multiplier to within ±0.04 of that identity.
So a prefilled player is effectively scored on their **observed** damage, while a player with no
logs stays at `mult = 1.0` and is scored on the **simulated** baseline. The two are aligned at
the roster median by construction, but not per spec: where `BASELINE` misjudges a spec, its
prefilled players carry the correction and its unprefilled ones do not. Concretely, in the live
run a 98.5th-percentile Beast Mastery hunter computed to 0.87, because `HUNTER:Beast Mastery`
holds the calibration table's highest value. This is inherent to prefilling only the players who
have logs — there is no data with which to correct the rest — so it is documented rather than
solved, and the UI names every unprefilled player so the gap is visible.

**Multipliers are not expected to track WCL percentiles.** A cross-check against `rankPercent`
on the same live run found only weak rank correlation (Spearman 0.15). That is the design
working, not failing: a 99th-percentile frost mage may deal less damage than a 60th-percentile
Beast Mastery hunter, and the optimizer wants the one who contributes more damage. §2 measures
output; a percentile measures standing within a spec. §7 rules percentile ratings out of scope
for exactly this reason.

**Why not the global population.** See the revision note above. Beyond reachability, a
roster-relative denominator has two genuine advantages: it is immune to partition/phase
mismatch (zone 1056 spans three phases, and a global median mixes guilds on gear your raid
does not have), and it costs one API query per player instead of a ~1,000-query sweep.

**Exclusions:**
- Healers are skipped entirely — their baseline is 0 by design, mult cannot matter. A zero or
  missing baseline also makes the ratio undefined, so they are excluded from `c(B)` too.
- Parses on a spec other than the rostered spec do not count. If a player has no
  qualifying same-spec parses in the window, they get **no prefill**: mult stays as-is and
  the UI marks them "no logs".

## 3. Architecture

Client (assignments.js) does the math with pure functions; server.js proxies WCL (same
pattern as the existing Raid-Helper proxy — WCL's OAuth secret cannot live in the browser).

### Auth

WCL API v2 (GraphQL, unified endpoint for retail + classic). Client-credentials flow:
`WCL_CLIENT_ID` and `WCL_CLIENT_SECRET` in the gitignored `.env` (the existing `.env` reader
picks them up). The server fetches a bearer token from `https://www.warcraftlogs.com/oauth/token`
and caches it in memory until shortly before expiry. Missing credentials → endpoints answer
503 with a clear message (mirrors the OpenAI-key behavior).

### Endpoints

- `GET /api/wcl/player?name=&server=&region=&zone=` — that character's
  `characterData.character.encounterRankings` per encounter in the zone (metric dps),
  returning per-parse `amount`, `spec`, and `startTime` so the client can apply the 4-week
  window and same-spec filter. One query, one GraphQL alias per encounter. Character names
  are URL-encoded; unknown character → 404 passed through as "no logs".

There is **no medians endpoint and no cache file** — the sweep they existed to amortize is
gone. The zone's encounter list is static, so the server resolves it once per zone and holds
it in memory for the process lifetime.

Endpoints validate inputs, use `AbortSignal.timeout`, and translate upstream failures to JSON
errors, matching the Raid-Helper proxy conventions. Upstream error handling must cover three
distinct shapes, all observed live: a non-2xx status, a GraphQL `errors` array at HTTP 200,
and a bare `error` string in the payload at HTTP 200 with no `errors` array. A proxy checking
only the status code reads the third as success.

### Zone and spec mapping

- The target zone is **1056** (SSC/TK, Anniversary), verified against the live API on
  2026-08-14. Two decoys exist: `1010` is the 2021 TBC Classic tier and `1052` is Titan
  Reforged. Two further traps: `worldData.zones` is stale and never lists 1056, so the zone
  must be addressed directly by id; and 1056's encounter ids are the 2021 ids **+100000**,
  where a bare 2021 id silently resolves to the 2021 tier instead of erroring.
- GraphQL is sent to the **`classic.`** host. `characterData` is host-scoped: `www` returns
  `character: null` for every real Anniversary character. The OAuth token endpoint stays on
  `www`. `startTime` on a rank entry is epoch milliseconds.
- WCL spec names ("Destruction", "BeastMastery", …) map to the engine's specKeys via an
  explicit table in the new pure module. Unmapped spec names are ignored (defensive), which
  means a parse logged under an Anniversary-invented spec contributes nothing rather than
  corrupting the ratio.
- **Known coverage limitation.** Zone 1056 uses spec labels the engine has no concept of —
  `Champion`, `Gladiator`, `Justicar`, `Warden`, `Dreamstate` — and a single character's
  `ranks[]` can mix several specs. A live sample of 14 characters found custom labels on 8 of
  them. Mapping these onto engine specs needs game knowledge the codebase does not contain
  (mapping a tank build onto a DPS baseline would produce a confidently wrong multiplier), so
  they stay unmapped: affected players get no prefill and the UI names them separately from
  genuinely unlogged players. Resolving the mapping is follow-up work, not part of this
  feature.

## 4. Client: computation module

New pure module `wcl-mult.js` (no DOM, UMD wrapper so Node and the browser share it),
exporting:

- `specNameToKey(className, specName)` → engine specKey or null.
- `playerBossMedians({ ranksByEncounter, classKey, specKey, nowMs, windowMs })` →
  `{ [encounterId]: medianAmount }` — applies the 4-week window and the same-spec filter,
  then takes the per-boss median of one player's parses. Exported separately so the filtering
  rules are unit-testable in isolation.
- `computeRosterMults({ players, nowMs, windowMs, minPlayersPerBoss })` →
  `{ [playerName]: { mult, bosses } }` — the two-pass computation of §2: per-player per-boss
  medians, then per-boss `c(B)`, then ratios, mean, clamp and rounding. Players with no
  qualifying data are absent from the result. `players` entries carry
  `{ name, classKey, specKey, baseline, ranksByEncounter }`; the caller supplies `baseline`
  so this module never depends on the engine.
- `shouldOverwrite(meta)` → whether a fetched value may replace `meta.mult` (see §5).

`nowMs` is a parameter (no hidden clock) so tests are deterministic.

## 5. UI workflow (assignments.js, Player tuning panel)

- Two new persisted settings fields: **server** (realm slug) and **region** — filled once.
- A **"Fetch from Warcraft Logs"** button. On click: fetch every eligible roster player's
  parses (one request each, with visible progress), then compute all multipliers in a single
  `computeRosterMults` pass, then write prefills. The two-pass shape is forced by §2 — no
  player's multiplier is known until the whole roster has been fetched.
- **Editable prefill with override protection:** `state.playerMeta[name]` gains `multAuto`
  (the last auto-computed value). A fetch overwrites `mult` only when the current `mult`
  equals the previous `multAuto` (or is unset/1.0-default) — i.e. auto values refresh, but a
  value the user has manually adjusted since the last fetch survives. Manual edits keep
  working exactly as today.
- Per-player provenance tooltip on the mult input, worded for a roster-relative number:
  e.g. "WCL: 1.12 vs this roster, from 6 bosses (fetched 2026-08-14)". Players with no data
  get a "no logs" marker and are left untouched.
- Errors (missing API key, 429, network) surface as a visible message in the panel, not
  silently.

## 6. Testing

- **Engine:** untouched; existing tests already cover `mult` propagation.
- **Unit tests** (existing node test setup): spec-name mapping including unmapped names;
  4-week window edges; same-spec filtering; per-boss median (odd/even counts); the per-boss
  `c(B)` fit including the outlier-resistance the median buys; cross-boss mean; the
  `minPlayersPerBoss` floor; clamp/rounding; no-data → null/absent.
- **Prefill/override logic:** unit-test the decision function (overwrite iff `mult ===
  multAuto` or unset) separately from the DOM.
- **Server endpoint:** `server.js` has no test harness and starting Express in tests is out
  of scope; it is covered by the live end-to-end run during implementation, which verifies
  the zone id, the alias-per-encounter query, the 404 path and the rank field names.

## 7. Out of scope

- Cross-spec inference (using fire parses to estimate arcane output).
- Percentile-based "skill only" ratings, blending, or ilvl-bracket normalization.
- Healer or per-boss weighting; automatic scheduled refresh; historical trending.
- Any absolute "how does my raid compare to the world" judgement — the revised §2 is
  deliberately relative to the roster.
